The AssuredCode Process

A procedure you can follow — and evidence you can audit.

Assurance is moved ahead of operational generation: the space from which software can be produced is constrained and qualified first, then verified again at generation and deployment before any artifact becomes operational. Follow the numbered steps to operate the process. Expand assurance detail to see what each step guarantees and how it is evidenced.

View
Steps are always shown in full. Only the assurance rationale expands.
01

Design time

Before generation
1.1Qualify the template against its approved specification.
Establishes the bounded space of software that can be produced. Nothing outside a qualified template can be generated.
Evidence — template qualification record
1.2Run combinatorial testing and simulation across the input space.
Exercises interactions across parameters before any live generation, surfacing defects at design time rather than in the field.
Evidence — combinatorial test coverage report
1.3Discharge the formal proofs for the template.
Correctness properties are proven, not sampled. Proof obligations are discharged in Lean 4 and retained.
Evidence — Lean 4 proof artifacts
02

Generation time

At production
2.1Normalize and bind the approved specification.
The same specification always normalizes to the same bound form — the basis of reproducible output.
Evidence — normalized spec hash
2.2Generate and compile the artifact.
Software is produced from a qualified grammar, then compiled — output is code that builds, not a suggestion to review.
Evidence — build record & artifact hash
2.3Run structural and semantic verification, then focused tests.
Each artifact is checked against structural and semantic expectations before it is eligible for deployment.
Evidence — verification & test results
03

Deployment time

Before it goes live
3.1Run the artifact in shadow execution.
Behavior is observed against live conditions with no operational effect before any activation.
Evidence — shadow execution log
3.2Obtain policy and human-in-the-loop approval.
Promotion requires explicit policy checks and a human decision — accountability is recorded, not implicit.
Evidence — approval & policy record
◇
Deployment gate — promotion refused unless obligations are discharged

The gate promotes an artifact only when every proof obligation is discharged and every check has passed. Fault injection that leaves an obligation undischarged causes the gate to refuse promotion. This is the process's hard stop.

3.3Activate via blue-green cutover.
The new artifact takes traffic only after the gate clears, with the prior version held ready for instant reversion.
Evidence — deployment receipt
3.4Monitor in production; roll back on deviation.
Operation is monitored continuously; any deviation triggers reversion to the last known-good version.
Evidence — monitoring & rollback log
Determinism

Same spec. Same artifact. Every time.

Unlike probabilistic code assistants that may generate different outputs from identical inputs, AssuredCode produces the same result every time from the same approved specification. Every generation is reproducible, auditable, and suitable for environments where consistency and accountability matter.

Probabilistic assistants
Same input, different output.
Non-reproducible. Every generation must be re-reviewed from scratch. Hard to audit, harder to certify.
AssuredCode
Same input, identical artifact.
Reproducible builds, traceable receipts, and proof obligations that must be discharged before promotion.
Key Capabilities

Controlled generation, end to end.

01

Deterministic generation

Generate software from approved specifications with reproducible outputs — enabling repeatable builds, validation, and compliance workflows.

02

Specification-driven

Software is generated from formal grammars, not free-form prompts. New languages and formats are added through grammar definitions — no foundation-model retraining.

03

Governance & auditability

Every generation ships with traceable artifacts: specifications, generation history, validation results, deployment receipts, and audit records.

04

Customer-controlled deployment

Operates entirely within customer-controlled environments. No generated source code leaves the customer boundary unless explicitly configured.

05

Enterprise validation

Integrated syntax checking, specification verification, and dependency governance. Fault injection leaves proof obligations undischarged — so the deployment gate refuses promotion.

06

Contextual knowledge sources

Integrate vendor-managed knowledge, customer repositories, or internal RAG — with full control over data access and governance policy.
